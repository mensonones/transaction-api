# Transaction API

A small Java 21 / Spring Boot API implementing the three endpoints from `Tech Case.pdf`.
PostgreSQL stores accounts and transactions. The code follows controller → service → repository,
with packages grouped by feature. There are no extra service interfaces or infrastructure layers.

## Requirements

- JDK 21 (Maven is provided by `mvnw`)
- Docker running, with Docker Compose v2
- Ports 8080 and 5432 available

## Run everything

```bash
./run
```

The script builds the application and uses the `app` profile in `compose.yaml` to start PostgreSQL
and the API. The API waits for the database health check. Data is stored in the `pgdata` volume.

Stop the containers without deleting the database:

```bash
docker compose --profile app down
```

## Run from IntelliJ or Maven

With Docker running, open the Maven project with JDK 21 and run `TransactionApiApplication`.
Use the project root as the working directory. Spring Boot starts PostgreSQL using `compose.yaml`.
Alternatively:

```bash
./mvnw spring-boot:run
```

Choose one execution mode at a time: the Docker API and the local API use the same ports.
Both modes use the PostgreSQL service and named volume defined in the same `compose.yaml`.
The `app` profile enables the API container only when running `./run`.

## Try the API

Open http://localhost:8080 (redirects to Swagger), or http://localhost:8080/swagger-ui.

Create an account (201):

```bash
curl -i -X POST http://localhost:8080/accounts \
  -H 'Content-Type: application/json' \
  -d '{"document_number":"12345678900"}'
```

Use the returned `account_id` in the following calls (examples assume `1`).

```bash
curl -i http://localhost:8080/accounts/1
curl -i -X POST http://localhost:8080/transactions \
  -H 'Idempotency-Key: payment-123' \
  -H 'Content-Type: application/json' \
  -d '{"account_id":1,"operation_type_id":1,"amount":50.00}'
```

The transaction response contains its ID, account ID, operation type, signed amount and event date.
For the purchase above, the stored and returned amount is `-50.00`.

| Operation ID | Description | Stored sign |
|---|---|---|
| 1 | Normal purchase | Negative |
| 2 | Purchase with installments | Negative |
| 3 | Withdrawal | Negative |
| 4 | Credit voucher | Positive |

## Requirements and implementation choices

The PDF requires account creation, account lookup, transaction creation, the four operation types,
and the sign rules. It permits an alternative data model: operation types are an enum here.
An installment purchase is recorded as one transaction; generating installments is outside the PDF scope.

The following are explicit API choices where the PDF does not specify behavior:

- Documents contain digits, have at most 32 characters and are unique. No CPF checksum validation.
- Requests supply positive amounts. The service determines the stored sign.
- Amounts use `BigDecimal` and `numeric(19,4)`: up to 15 integer digits and 4 decimal places.
  Values outside that range return 400 instead of being silently rounded by the database.
- IDs and event timestamps are generated by the application/database, not supplied by the client.
- Invalid input returns 400; missing accounts or unknown operation types return 404;
  duplicate documents return 409. Unexpected errors use Spring Boot's default 500 response, with internal messages and stack traces excluded.
- A database unique constraint protects documents under concurrent requests. The service translates PostgreSQL unique violations
  (SQLState 23505) to 409. Document number is the only client-controlled unique field; IDs are generated.
  If more unique fields are introduced, this mapping should be revisited.

The local credentials and Hibernate `ddl-auto: update` are conveniences for this exercise.
A production deployment would need environment-specific configuration and versioned database migrations.

## Transaction idempotency

`POST /transactions` requires the `Idempotency-Key` header. Missing, empty or invalid keys return 400.
Keys are case-sensitive, 1–128 characters: letters, digits, dots, underscores, colons or hyphens.
Generate a new key (for example a UUID) for each new operation; keep the same key when retrying it.

- Same key and same account, operation and amount: returns the original transaction with 201,
  including its original ID and timestamp. Decimal values such as 12.34 and 12.3400 are equivalent.
- Same key with different valid transaction data: 409 Conflict.
- Different keys: independent transactions, even with identical bodies.
- Keys are global to this endpoint and retained with the transaction, without expiration.
- Invalid input, unknown operation or missing account do not reserve a key. Retries are validated too.

## Error responses

All error bodies use `application/json`. Field names follow snake_case throughout, including in
error payloads — HTTP header names are converted (e.g. `Idempotency-Key` → `idempotency_key`).

| Scenario | Status | Body |
|---|---|---|
| Business rule violation (not found, conflict) | 404 / 409 | `{"error": "<message>"}` |
| Validation failure (missing or invalid field / header) | 400 | `{"errors": {"<field>": "<message>", …}}` |

Examples:

```json
{"error": "Account not found"}
{"errors": {"account_id": "must not be null", "amount": "must be greater than 0"}}
{"errors": {"idempotency_key": "header is required"}}
{"errors": {"idempotency_key": "size must be between 1 and 128 characters"}}
```

The key is stored on the transaction with a unique constraint. PostgreSQL's
`INSERT ... ON CONFLICT DO NOTHING` prevents concurrent requests from inserting twice.
The service reads and checks the stored transaction in the same database transaction.
There is no extra service or in-memory cache. Hibernate adds the nullable column on startup:
old transactions remain without keys; all new API requests require one.

## Tests

```bash
./mvnw test       # isolated tests with Surefire; no Docker needed
./mvnw verify     # isolated tests plus integration tests with Failsafe; Docker required
```

`*Test` / `*Tests` are isolated tests. `*IT` tests use Spring, MockMvc and a disposable PostgreSQL 16
container. They cover the endpoints, validation, stored amounts, database uniqueness and duplicate
account creation. Test tables are cleared between integration tests without restarting Spring.
The integration database is separate from the development database.
